## Dochestra RFP

### 01. 프로젝트 개요

> Dochestra는 사용자가 캔버스에 노드를 배치하고 연결해 만든 워크플로를 실행하는 웹 애플리케이션이다. 캔버스 하나에 워크플로 하나를 담고, 여러 캔버스의 흐름을 각각 저장하고 다시 열 수 있다.

#### 1.1. 사용 대상과 목표

사용자는 작업마다 캔버스를 만들고 노드를 보기 편한 위치에 놓는다. 실행기는 연결선을 따라 앞 노드의 출력을 다음 노드로 전달한다. 화면에서 노드를 옮겨도 연결이 같으면 실행 순서는 유지된다.

#### 1.2. 실행기의 책임

| 대상 | 담당하는 동작 |
| --- | --- |
| 캔버스 | 캔버스 생성·전환, 노드 추가·이동·삭제, 화면 이동과 확대·축소, 연결 편집을 제공한다. |
| 워크플로 | 노드와 연결을 검증하고 실행한다. 캔버스별로 설정과 배치를 저장하고 복원한다. |
| 개별 노드 | 파일 입력을 비롯한 구체적인 처리 기능은 해당 노드가 제공한다. 실행기는 등록된 노드의 입출력 규칙에 따라 데이터를 전달한다. |

#### 1.3. 캔버스별 실행 규칙

캔버스 하나는 워크플로 하나를 담는다. 실행할 때는 시작 노드 1개에서 끝 노드 1개까지 모든 노드가 한 경로로 이어져야 한다. 실행기는 연결 순서대로 한 노드씩 실행하며, 이 규칙은 각 캔버스에 독립적으로 적용된다.

## 02. 요구사항

U는 사용자 행동, O는 운영자의 책임, S는 시스템이 보장할 동작을 뜻한다.

#### 2.1. 사용자 요청

| 요청 | 완료 조건 |
| --- | --- |
| U05  캔버스 관리 | 캔버스를 여러 개 만들고 전환한다. 각 캔버스는 워크플로 하나를 가지며, 편집·저장·실행은 선택한 캔버스에만 적용한다. |
| U02  흐름 편집 | 노드를 원하는 위치로 옮기고 화면을 이동·확대·축소한다. 연결을 추가·해제하거나 중간에 노드를 끼울 수 있다. 노드를 지우면 연결된 선도 지운다. |
| U04  저장·재사용 | 노드 유형과 설정값, 노드별 위치, 연결을 함께 저장한다. 브라우저를 닫았다 다시 열어도 저장한 캔버스에서 편집과 실행을 이어갈 수 있다. |
| U03  실행 확인 | 현재 캔버스에서 실행을 시작하고 노드별 진행 상태와 실행 결과를 확인한다. |

#### 2.2. 운영·시스템 요청

| 요청 | 완료 조건 |
| --- | --- |
| O01  시연 운영 | 팀이 접속 주소와 예시 워크플로를 준비한다. 캔버스 두 개를 각각 편집하고 저장·복원·실행할 수 있는지 확인한다. |
| S01  실행 전 검사 | 시작과 끝이 각각 1개인지, 모든 노드가 단일 경로에 속하는지 검사한다. 분기·합류·순환·끊긴 경로, 미등록 노드, 입출력 불일치가 있으면 실행을 막고 이유를 표시한다. |
| S02  실패와 재실행 | 노드가 실패하면 해당 위치와 원인을 표시하고 실행을 멈춘다. 설정과 연결은 보존해 수정 후 다시 실행할 수 있게 한다. |
| S04  노드 확장 | 공통 입출력 규칙을 따르는 새 노드를 등록하면 캔버스에서 선택해 실행할 수 있다. 새 유형을 추가할 때 실행 순서를 결정하는 로직은 그대로 사용한다. |

## 03. 제약 조건

#### 3.1. 시연 완료 기준 제안

| 확인할 동작 | 시연에서 확인할 결과 |
| --- | --- |
| 캔버스 독립성 | A와 B에 시작과 끝을 각각 하나씩 두고 두 흐름을 실행한다. A에서 추가 분기를 시도하면 해당 연결 또는 실행을 막고, B는 기존 흐름대로 실행된다. |
| 배치와 실행 | A에서 앞뒤 노드의 화면 위치만 맞바꾼다. 같은 입력에서 실행 순서와 결과는 그대로이고, 저장 후 다시 열면 바꾼 위치가 복원된다. |
| 새 노드 삽입 | 기존 흐름 중간에 새로 등록한 예시 노드를 연결해 저장한다. 다시 열어 실행하면 해당 노드의 출력이 다음 노드에 전달된다. |

#### 3.2. 개발 환경

부산 해커톤의 제한 시간 안에 3명이 개발한다. 개발 계획은 EC2 한 대에서 Linux 계정 3개와 개별 Claude Code 세션을 사용하고, hcom으로 설계·통합 1개 세션과 개발 2개 세션을 연결하는 방식이다.

EC2 사양과 비용은 확정 전이다. 첫 시연은 외부 서비스 연결 없이 동작하는 예시 노드로 진행할 수 있다.

## Dochestra 사용자·역할·서비스 경계

### 01. 사용자와 역할

> 사용자는 캔버스마다 하나의 워크플로를 만들고 실행한다. 노드 제공자는 새 기능을 등록하고, 시연 담당자는 사용자와 같은 화면에서 준비한 흐름을 점검한다.

| 역할 | 달성하려는 결과와 책임 |
| --- | --- |
| 캔버스 사용자 | 작업별로 캔버스를 만들고 노드를 배치·연결한다. 위치와 설정을 저장하고, 선택한 캔버스의 실행 상태와 결과를 확인한다. |
| 노드 제공자 | 개발팀에서 새 노드 유형의 입출력·설정·처리 동작을 정의해 등록한다. 등록된 유형을 사용자가 자기 캔버스에 추가할 수 있도록 한다. |
| 시연 담당자 | 접속 주소와 예시 워크플로를 준비한다. 캔버스 두 개를 독립적으로 저장·복원·실행할 수 있는지 사용자 화면에서 확인한다. |

#### 1.1. 계정과 작업 범위 제안

첫 시연은 별도 회원가입 없이 같은 브라우저 프로필에서 저장한 캔버스를 다시 여는 방식으로 제안한다. 이때 같은 프로필을 사용하는 사람은 같은 작업 공간에 접근한다. 개인 문서의 비공개 보관이나 사용자 간 공유는 이번 접근 방식의 보장 범위 밖이다.

팀원 한 명이 세 역할을 겸할 수 있다. 시연 담당자는 예시 캔버스를 열면 사용자와 같은 편집 범위를 갖는다. 개발 서버의 Linux 계정과 Claude 세션은 개발 협업에 쓰인다.

## 02. 행위별 권한과 적용 범위

표는 각 역할이 수행할 수 있는 행위와 그 효과가 미치는 대상을 함께 표시한다.

| 역할·대상 | 허용 행위 | 영향 범위 |
| --- | --- | --- |
| 사용자 · 작업 공간 | 캔버스 생성·전환·다시 열기 | 선택한 캔버스의 워크플로 하나가 편집·실행 대상이 된다. |
| 사용자 · 선택한 캔버스 | 등록된 유형을 배치·설정하고 연결·저장·실행 | 배치한 노드를 삭제하면 해당 캔버스에서 그 노드와 연결선만 제거된다. 노드 목록과 다른 캔버스는 유지된다. |
| 노드 제공자 · 유형 목록 | 새 유형을 구현해 등록 | 선택 가능한 유형이 늘어난다. 각 캔버스에 넣을지는 사용자가 정한다. |
| 시연 담당자 · 예시 캔버스 | 사용자 자격으로 편집·저장·실행 | 시연 준비 역할에 다른 사용자의 작업을 관리하는 권한은 부여하지 않는다. |

#### 2.1. 실행 요청을 받아들일 조건

현재 캔버스의 시작과 끝이 각각 1개이고, 모든 노드가 단일 경로로 이어져야 한다. 분기·합류·순환·끊긴 연결, 미등록 유형, 입출력 불일치가 있으면 위치와 이유를 표시한다. 수정할 수 있도록 구성은 보존한다. 실행 중 노드가 실패해도 해당 위치에서 멈추고 설정과 연결을 유지한다.

#### 2.2. 한 캔버스의 변경이 미치는 범위

사용자가 A에 놓인 중간 노드를 삭제하면 A의 경로가 끊겨 실행이 보류된다. 남은 노드를 다시 연결하면 A를 실행할 수 있다. 같은 유형의 노드를 사용한 캔버스 B는 이전 구성 그대로 실행할 수 있다.

## Dochestra 현재 업무 분석

### 01. 작업을 다시 실행할 때 생기는 문제

분석 가정 · 반복 작업을 개별 도구나 스크립트로 나눠 수행하는 상황을 다룬다. 특정 기업의 실제 절차와 발생 빈도는 확인되지 않았다.

> 개별 단계에서 원하는 결과를 얻더라도, 다음 작업에서 같은 순서·설정·중간 결과를 다시 맞춰야 한다. 처리 단계를 하나 바꾸면 그 영향을 어디까지 확인해야 할지도 달라진다.

| 관련 역할 · 문제 | 현재 작업 방식 | 발생하는 어려움 |
| --- | --- | --- |
| 캔버스 사용자<br>P01  단계 간 전달 | 첫 도구에서 나온 값을 골라 다음 도구에 입력한다. | 이전 실행의 값을 옮겨도 다음 도구가 그대로 처리할 수 있어, 결과가 어느 입력에서 나왔는지 다시 확인한다. |
| 캔버스 사용자<br>P02  순서 재현 | 이전 작업의 메모와 결과를 보고 단계 순서와 옵션을 재구성한다. | 결과가 예상과 다르면 입력, 순서, 옵션 중 무엇이 달랐는지 대조해야 한다. |
| 노드 제공자<br>P03  도구 인계 | 새 처리 도구를 만들고 입력 형식과 출력 예시를 전달한다. | 앞뒤 도구의 형식이 맞지 않으면 단독 실행에 성공해도 연결 지점을 다시 조정해야 한다. |
| 시연 담당자<br>P04  시연 재현 | 준비한 입력과 안내 메모로 같은 절차를 수행하고 예시 결과와 비교한다. | 결과가 다르면 개별 단계의 출력을 찾아 차이가 시작된 지점을 좁혀야 한다. |

#### 1.1. 분석 범위

한 작업의 단계 연결, 새 처리 도구의 인계, 시연 재현까지 다룬다. 파일 형식이나 번역 품질처럼 개별 도구의 기능에 달린 문제는 실행기의 필요성을 판단하는 근거에서 제외한다.

## 02. 반복 작업을 다시 수행하는 과정

NF는 비기능, REL은 신뢰성, SEC는 접근·보안, PER은 성능이다. 아래 수치는 해커톤 검수용 제안값이다.

## 04. 사용자 유형과 이용 상황

사용자 조사 전의 가정형 페르소나다. 한 사람이 여러 역할을 겸할 수 있다.

| 역할과 목표 | 상황·행동 | 설계에서 보장할 일 |
| --- | --- | --- |
| 반복 작업 담당자<br>기존 흐름 재사용 | 지난번 작업과 비슷한 입력을 받는다. 캔버스 A를 열어 처리 단계 하나만 바꾸고, B는 원래 상태로 남기려 한다. | 현재 캔버스 이름, 저장 여부, 실행 대상이 같은 화면에서 읽혀야 한다. |
| 노드 제공자<br>새 처리 방식 인계 | 문자열에 접두어를 붙이는 함수를 제공한다. 다른 팀원이 코드를 고치지 않고 이를 흐름에 넣길 원한다. | 유형 식별자와 설정·입출력을 선언하고, 최소 샘플로 목록 노출과 전달을 확인한다. |
| 시연 담당자<br>결과 재현 | 발표 직전 두 흐름을 차례로 확인한다. 마지막 단계까지 성공해도 기대 문자열과 다르면 재점검한다. | 실패 위치와 실제 최종값을 보여준다. 업무상 정답 여부는 담당자가 대조한다. |

#### 접근과 데이터

개인 정보가 없는 예시 데이터로 시연한다. 같은 브라우저 프로필을 공유하면 저장 목록도 공유된다. 기기를 바꾸거나 브라우저 사이트 데이터를 지우면 기존 목록을 사용할 수 없다.

## 7.1. 실행 계약과 확장 규칙

| 경계 | 서로 지켜야 할 약속 |
| --- | --- |
| 목록 응답 | typeKey, version, label, role(start/step/end), inputType, outputType, fields를 반환한다. 등록 키는 (typeKey, version) 쌍이다. 서버 시작 시 중복·누락 핸들러가 있으면 준비 실패로 처리한다. |
| 실행 요청 | POST /api/runs에 runId, canvasId, nodes, edges, input을 보낸다. node는 id, typeKey, version, config로 구성한다. edge는 id, source, target이다. 좌표는 보내지 않는다. |
| 실행 응답 | 성공적으로 시작하면 HTTP 200 · application/x-ndjson. 각 줄은 runId, seq, event와 해당 시 nodeId를 포함한다. node.started, node.succeeded가 순서대로 오며 run.completed에 output을 담는다. |
| 실패 응답 | 실행 전 422는 code, message와 관련 nodeId 또는 edgeId를 담는다. 본문 크기 초과 413, 동시 처리 한도 429. 실행 중 실패는 run.failed 이벤트로 종료하고 code와 nodeId를 남긴다. |
| 노드 제공자 | 역할·입출력·필드 명세와 핸들러를 등록한다. 내장 노드는 텍스트를 입출력하며 start는 실행 입력을 읽고 end는 최종 값을 반환한다. 새 문자열 설정은 기존 편집기 필드로 표시한다. |
| 등록 범위 | 제공자가 신뢰된 서버 코드로 등록하고 재시작한다. 임의 스크립트 업로드와 동적 코드 평가는 제공 범위 밖이다. 다른 형식의 필드 UI나 부작용이 있는 외부 노드는 별도 설계가 필요하다. |

시연 기준값 · input = A-01, prefix = “DEMO ”. 끝 노드의 기대 출력은 “DEMO A-01”이다. 전송 청크가 줄 중간에서 나뉘면 브라우저는 줄바꿈까지 모아 해석한다.

첫 통합용 명세 · prefix@1은 text 하나를 받아 text 하나를 반환한다. fields에는 key=prefix, type=string, required=true를 선언한다. 빈 문자열과 뒤 공백도 값으로 보존하고, 누락·알 수 없는 키·문자열 이외의 값은 실행 전에 거절한다. 세션은 runId가 일치하고 seq가 증가하는 이벤트만 반영한다.

<a id="p25"></a>

## 8.1. 네트워크·보안·장애 범위

| 위치 | 허용 범위와 제어 |
| --- | --- |
| 외부 진입 | 443은 시연 사용자에게 허용한다. 22는 팀원 접속 IP로 한정한다. 80은 인증서 발급 또는 HTTPS 전환에 필요할 때만 연다. 8000은 127.0.0.1에 바인딩한다. |
| 웹 실행 | 정적 화면과 /api는 동일 출처다. 브라우저 실행 요청의 Origin을 검사하고 임의 교차 출처를 허용하지 않는다. 공개 API에는 서버 측 크기·건수·동시 실행 제한도 적용한다. |
| 데이터·비밀 | 샘플 텍스트만 시연한다. 결과는 텍스트로 렌더링한다. 브라우저 저장소에는 캔버스 구성만 기록하며 비밀 키를 설정 항목에 넣지 않는다. 요청 본문과 결과는 로그에서 제외한다. |
| 서버 부하 | 1프로세스에서 동시에 최대 3회 실행하도록 제안한다. 전체 실행 제한 30초, 초과 시 중단하며 새 요청은 빈 자리가 없으면 429로 응답한다. 내장 노드는 제한 내 유한한 작업만 수행한다. |
| 개발 계정 | 팀원별 일반 Linux 사용자와 SSH 키를 둔다. 공용 Git 데이터에 팀 그룹 권한을 준다. hcom 연동 환경은 서로 세션 제어를 신뢰하는 팀 전용으로 한정한다. |
| 단일 장애점 | 서버 정지 시 공개 화면 접속과 실행이 중단된다. 같은 주소로 배포를 복구하면 브라우저 저장본을 다시 읽는다. 실행 메모리는 복구 대상에서 제외한다. |

복구 제안 · 첫 시연 커밋과 잠금 파일을 서버 밖 팀 PC에 보관한다. 정적 빌드와 서버 등록부를 같은 커밋에서 재배포한다. 개인 브라우저 데이터 삭제·기기 분실로 사라진 캔버스에는 서버 백업이 없다.

## 8.3. 시연 자원과 복구 기준

| 자원·운영 | 제안 기준과 확인 방법 |
| --- | --- |
| 메모리 예산 | 운영체제·프록시·API에 3 GiB, 개발 세션 3개에 합계 6 GiB, 동시 빌드에 4 GiB, 여유 3 GiB를 잡는다. 합계 16 GiB이며 실제 사용량은 리허설에서 확인한다. |
| 요청량 | 동시 실행 최대 3개 × 요청 64 KiB = 실행 본문 최대 192 KiB. 정적 자산·TLS·실행 중 임시 객체는 별도다. 세션별 실측이 서버 선택 기준이다. |
| 상태 확인 | 통합 담당자가 /api/node-types 응답, HTTPS 인증서, 메모리·디스크 여유와 429·5xx 발생 여부를 본다. 단일 프로세스 장애 시 재시작 후 공개 샘플을 재실행한다. |
| 백업·복구 | 첫 통합 성공 시와 제출 직전의 Git 커밋을 팀원 PC에 별도 복사한다. 두 사본을 심사 종료까지 유지하고 깨끗한 폴더에서 열어 제출 커밋과 잠금 파일을 대조한다. |
| 재개 순서 | Git 사본 확보, 의존성 복원, 정적 앱 빌드, API와 프록시 기동, 동일 HTTPS 주소에서 시연 샘플 재검증 순이다. 저장된 브라우저 프로필의 복원 여부도 확인한다. |

하드웨어 수치는 발주·구매 조건이 아니다. 비용·크레딧·동시 세션 사용 가능성은 팀이 실제 계정에서 확인할 항목이다.

편집 초안은 비어 있거나 경로가 끊겨도 저장한다. 실행 시 시작·끝 각 1개, 같은 캔버스의 노드만 참조, 노드 수에서 1을 뺀 연결 수와 실제 단일 경로를 함께 검사한다.

| PR02·03·06 편집 | D01\~03 편집 사본, D04 설정 규칙 | 캔버스 ID별 초안에 배치 노드·연결을 추가·변경·삭제한다. |
| PR07 저장·복원 | D01 revision과 기존 레코드 | D01\~03을 한 객체로 교체한다. 브라우저 종료 전 명시적으로 저장한 버전을 복원한다. |

#### 초기화와 데이터 호환

IndexedDB onupgradeneeded에서 canvases 저장소를 만들고 거래 완료 후 초기 목록을 읽는다. 앱은 이미 존재하는 유형·버전의 의미를 바꾸지 않는다. 새 의미는 새 버전으로 등록한다. 미지원 데이터 형식을 읽으면 기존 레코드를 덮어쓰지 않는다.

시연 노드 세트 제안 · start@1은 실행 입력 text를 출력하고, prefix@1은 text를 받아 설정값 prefix와 이어 붙인다. end@1은 text를 받아 최종 결과로 반환한다. 일반 처리 노드는 설정만 저장하며 실행 입력은 매번 지정한다.

## 9.2. 논리 모델과 수명

| 정보 · 식별자 | 관계와 무결성 | 생성·보존 |
| --- | --- | --- |
| D01 캔버스<br>id | 이름, revision, 갱신 시각, 문서 포맷 버전. 워크플로는 캔버스에 종속된 단일 집합이다. | 생성 시 새 UUID. 명시적 저장 후 같은 출처·프로필에서 유지. |
| D02 배치 노드<br>(canvasId, nodeId) | 한 노드는 해당 캔버스의 등록 유형 1개 및 버전을 참조한다. 좌표 변경과 연결 변경은 독립적이다. | 설정·좌표를 저장한다. 삭제 시 같은 초안의 직접 연결만 함께 삭제. |

동시 편집 · 같은 캔버스를 두 탭에서 열면 먼저 완료된 저장이 기준이다. 오래된 revision으로 저장하면 충돌을 알리고 사용자가 초안을 확인한 뒤 최신 저장본을 다시 열 수 있게 한다.

## 9.4. 물리 저장과 원자성

저장 기술 제안 · IndexedDB 데이터베이스 dochestra, 버전 1, 객체 저장소 canvases. 캔버스별 레코드 한 건으로 관련 구성 전체를 저장한다.

| 필드 · 저장형 | 필수 조건 · 기본값 |
| --- | --- |
| id / name | 필수 문자열. id는 UUID이자 keyPath. name은 양끝 공백 제거 후 1\~60자. 생성 시 기본 이름을 부여하며 이름 중복은 허용한다. |
| schemaVersion / revision | 필수 정수. 포맷 버전 1, 신규 편집본 revision 0. 최초 저장 1, 이후 성공 시에만 1 증가한다. 미지원 포맷은 쓰기 전 거절한다. |
| updatedAt | 필수 숫자. 커밋할 때 기록하는 Unix 밀리초. 목록은 updatedAt 내림차순, 동률이면 id 순으로 표시한다. |
| nodes[] | 필수 배열, 0\~32개. id(UUID), typeKey(1\~64자), version(양의 정수), config(명세에 맞는 객체), x·y(유한 숫자). 신규는 시작과 끝으로 초기화한다. |
| edges[] | 필수 배열, 0\~31개. 각 항목의 id·source·target은 UUID 문자열이다. 신규는 시작에서 끝으로 향하는 연결 1개다. |
| 인덱스·거래 | 기본키 id로 직접 조회한다. 소규모 목록은 getAll 후 정렬한다. 단일 readwrite 트랜잭션에서 저장본 revision 조회·비교·put을 수행한다. 완료 이벤트 뒤 저장 성공으로 표시한다. |

저장 오류 · 충돌 또는 저장소 한도 초과로 거래를 중단하면 기존 레코드를 보존한다. 캔버스 ID가 다르면 별도 레코드다. 서버에는 캔버스 DB를 두지 않는다.

실패 확인 · 연결 한 개를 끊고 실행하면 서버가 호출 전에 거절한다. 처리 함수가 실패하면 뒤 노드는 실행되지 않는다. 서버 중지 또는 단절 시 화면은 실패 또는 완료 미확인을 표시하고 편집 사본을 보존한다.

이 항목은 개발·배포 담당자가 확인할 인수 기준이다. 소프트웨어 구현, 계정 연결, 성능 측정과 배포는 실행 전이다.
