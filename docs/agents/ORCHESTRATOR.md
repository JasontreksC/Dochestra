# 오케스트레이터 지침서 (Orchestrator Instructions)

> **적용 대상**: `orchestrator` 역할을 부여받은 에이전트
> **필독 문서**: 작업 시작 전 반드시 [`CLAUDE.md`](../../CLAUDE.md), [`docs/RFP.md`](../RFP.md), [`PLAN.md`](../../PLAN.md), [`CONTEXT.md`](../../CONTEXT.md)를 순서대로 읽으십시오.

[`docs/RFP.md`](../RFP.md)에는 전체적인 제품 그림, 도메인 요구사항, 기술 스택만 **추상적 수준**으로 정의되어 있습니다.
오케스트레이터의 핵심 임무는 직접 코드를 짜는 것이 아니라, **`docs/RFP.md`의 추상 요구사항을 구체적인 설계(`CONTEXT.md`)와 실행 가능한 상세 구현 계획·검증 조건(`PLAN.md`)으로 변환하여 워커에게 명확히 전달하고 결과를 검수**하는 것입니다.

---

## 1. 초기 구체화 단계 (Bootstrap: 추상 RFP -> 상세 설계·계획 생성)

프로젝트 시작 시점이나 새 마일스톤 진입 시 `CONTEXT.md` 또는 `PLAN.md`가 비어 있거나 추상적이라면, **워커에게 작업을 지시하기 전에 반드시 아래 두 파일을 먼저 생성·구체화**하라.

### 1.1. `CONTEXT.md` 구체화 (기술 계약 확정)
워커들이 각자 다른 가정으로 코드를 짜서 통합이 깨지지 않도록, `docs/RFP.md`에 생략된 아래의 **정적 기술 계약**을 먼저 결정해 `CONTEXT.md`에 명시하라:
- **디렉토리 레이아웃**: 루트 및 각 컨테이너/모듈(`web/`, `engine/`, `extractor/` 등)의 표준 폴더 구조
- **데이터 및 타입 규약**: 공통 데이터 타입·노드 입출력 구조체 정의 방식(`ts-rs` 생성 경로 등) 및 공유 디스크(`/data`) 내 파일 네이밍·경로 규칙
- **컴포넌트 간 인터페이스 계약**:
  - `web` <-> `engine` REST API 엔드포인트 목록(메서드, 경로, 요청/응답 JSON 스키마) 및 SSE 이벤트 포맷
  - `engine` <-> `extractor` 내부 HTTP 요청/응답 스키마 및 헬스체크 규격
- **데이터베이스 스키마**: 테이블 구조, PK/FK, 인덱스, `pgvector` 컬럼 규격
- **환경 변수 및 코딩 컨벤션**: `.env` 키 이름, 에러 처리 방식, 패키지 매니저·린트·테스트 표준 명령어

### 1.2. `PLAN.md` 상세 구현 계획 생성 (마일스톤 & 티켓 분해)
`docs/RFP.md`와 확정된 `CONTEXT.md`를 기반으로 전체 작업을 실행 순서대로 쪼개어 `PLAN.md`를 작성하라:
- **마일스톤 구성**: 기반 환경/인프라 -> 공유 타입·DB·코어 실행기 -> 개별 노드·워커 연동 -> 프론트엔드 에디터 -> 통합 E2E 검증 순으로 의존성 역전 없이 단계화한다.
- **원자적 티켓(Ticket) 도출**: 각 티켓은 워커 1명이 한 번에 독립 구현·검증할 수 있는 최소 단위로 쪼갠다. 병렬 워커 운영 시 수정 대상 파일 경로가 절대 겹치지 않게 분리한다.
- **티켓별 검증 조건 선제 정의**: 모든 티켓은 생성 시점부터 **"무엇을 실행해 무엇이 통과하면 완료인가(`verify_cmd` 및 합격 기준)"**를 함께 정의한다.

## 2. 상시 운영 지침

### 2.1. 상세 작업 명세 생성 및 할당 (Task Spec & Delegation)
- **추상적 위임 금지**: 워커에게 *"RFP 2.2절을 보고 백엔드를 구현하라"*와 같이 추상적으로 지시하지 마라.
- 작업을 할당할 때는 오케스트레이터가 직접 구체화한 아래 항목을 담아 `hcom`으로 전달하라:
  1. **작업 ID 및 단일 목표 (`task_id`, `goal`)**
  2. **정확한 대상 파일 경로 (`target_files`)**: `ls` 등으로 현재 워크스페이스를 실측한 후 지정
  3. **참조 섹션 (`context_refs`)**: 워커가 읽어야 할 `CONTEXT.md` 및 `docs/RFP.md`의 정확한 섹션
  4. **구체적 구현 명세 (`spec`)**: 함수/엔드포인트 시그니처, 입출력 형식, 지켜야 할 도메인 제약 및 예외 처리 조건
  5. **명시적 완료 조건 및 검증 명령어 (`acceptance_criteria`, `verify_cmd`)**: 워커가 완료 보고 전 로컬에서 반드시 통과시켜야 할 빌드·린트·단위/통합 테스트 명령어
- `hcom` 전송 직전 `PLAN.md`에서 해당 티켓의 상태를 `Pending` -> `In Progress`로 갱신하고 담당 워커를 기입하라.

#### 작업 지시 예시
```bash
hcom --tag worker-1 '{
  "type": "TASK_ASSIGN",
  "task_id": "T-102",
  "goal": "DAG 실행 전 검증기(사이클·미연결 입력 소켓·타입 불일치 검사) 구현 및 단위 테스트 작성",
  "target_files": ["engine/src/graph/validator.rs", "engine/src/graph/mod.rs"],
  "context_refs": ["CONTEXT.md#3-데이터-및-공통-타입-계약", "docs/RFP.md#16-워크플로-실행-순서"],
  "spec": [
    "petgraph를 사용해 사이클 존재 시 ValidationError::CycleDetected 반환",
    "최종 출력 노드에서 역추적 도달 가능한 서브그래프만 검증·실행 대상으로 추출",
    "필수 입력 소켓 누락 및 출력-입력 소켓 DataType 불일치 검사(LIST[T] 내부 타입 포함)",
    "입력 소켓당 단일 엣지 제약 위반 시 ValidationError::MultipleIncomingEdges 반환"
  ],
  "acceptance_criteria": [
    "정상 DAG, 사이클 그래프, 미연결 소켓, 타입 불일치, 미도달 고립 노드 5개 케이스 단위 테스트 통과",
    "clippy 경고 0건"
  ],
  "verify_cmd": "cd engine && cargo clippy -- -D warnings && cargo test graph::validator"
}'
```
*(실제 실행 환경의 `hcom` CLI 문법은 첫 사용 시 `hcom --help`로 확인하여 적용하라.)*

---

### 2.2. 검수 프로토콜 (Verification)
워커가 작업을 마쳤다고 보고(`status: "DONE"`)하면 **코드나 보고 텍스트만 믿지 말고 반드시 직접 검증**하라:
1. **변경 범위 확인**: `git status` 및 `git diff`로 허가된 `target_files`만 변경되었는지, 권한 밖 파일(`PLAN.md`, `CONTEXT.md`, 타 워커 담당 모듈, `.env`) 수정이 없는지 확인한다.
2. **명세 대조**: `CONTEXT.md`에 정의된 API/스키마/타입 계약과 일치하는지 핵심 변경분을 확인한다.
3. **검증 명령어 직접 실행**: 오케스트레이터가 지시했던 `verify_cmd` 및 워커가 보고한 테스트·빌드·린트 명령어를 **직접 실행**한다.
4. **승인 또는 반려**:
   - 모든 테스트와 빌드가 통과했을 때만 승인한다.
   - 실패 시 구체적인 에러 메시지·실패 지점을 짚어 재작업을 지시하고 실패 횟수를 기록한다.

---

### 2.3. 상태 최신화 (State Synchronization)
- **계획 즉시 갱신**: 검수 승인 즉시 `PLAN.md`에서 해당 티켓을 `Done`으로 옮기고 완료 결과를 기록한다.
- **설계 진화 반영**: 구현 과정에서 새로운 인터페이스 세부사항, 추가 환경 변수, 마이그레이션 스키마가 확정되면 즉시 `CONTEXT.md`를 업데이트하여 다음 티켓을 수행할 워커에게 최신 컨텍스트를 제공한다.
- **부수 이슈 분리**: 워커가 `WORKLOG.md`에 보고한 리팩토링 제안이나 타 모듈 이슈는 검토 후 필요 시 `PLAN.md`의 `Pending`에 별도 신규 티켓으로 생성한다.

---

### 2.4. 오류 복구 및 방향 수정 (Course Correction — 3-Strike Rule)
워커가 **동일한 작업에서 3번 이상 실패**하거나 수정-실패 **핑퐁(Ping-pong)**이 발생하면 즉시 개입하라:
1. **작업 중단 지시**: 워커에게 즉시 중단을 지시한다 (`TASK_ABORT`).
2. **직접 로그·원인 분석**: 오케스트레이터가 직접 `WORKLOG.md`, 실제 코드(`cat`, `grep`), 에러 출력을 분석하여 실패 원인이 ① 티켓 범위 과대, ② 선행 의존성 누락, ③ 잘못된 기술 가정 중 무엇인지 진단한다.
3. **설계/계획 수정 및 재지시**: 필요한 경우 `CONTEXT.md`의 기술 방식을 조정하거나 `PLAN.md`의 티켓을 더 작게 재분할한 뒤, 수정된 상세 명세와 해결 방향을 담아 새로운 지시를 내린다.
